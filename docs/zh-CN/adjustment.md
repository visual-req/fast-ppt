# 调整指南

这份文档专门讲三类最常见的回改动作：

- 怎么调整 PPT 的章节结构
- 怎么增加或替换 SVG 图示
- 怎么修改 layout 的使用方式或渲染效果

如果你现在已经发现“这份 PPT 不太对”，但还不确定该改哪一层，先看这页最合适。

## 先判断该改哪一层

很多回改之所以越改越乱，不是因为不会改，而是因为改错了层。

先用这张表判断：

| 现象 | 优先回改层 | 主要文件 |
|------|------------|----------|
| 章节顺序不对、结构不顺 | 结构层 | `outline.json` |
| 某一页内容方向对，但表达不够图形化 | 页面层 + 资产层 | `slides/*.json` + `work/assets/*.svg` |
| 某个 layout 不适合、不好看、字段不够 | 规则层 + 渲染层 | `skills/prompts/ppt/layouts.md` + `ppt-viewer/src/components/layouts/*.vue` |
| viewer 能看，但导出不一致 | 导出层 | `ppt-viewer/src/lib/*` + `lib/pptxExport.mjs` |
| 同类项目总是生成错结构 | 提示词规则层 | `skills/prompts/ppt/01_课件类.md` ~ `04_演示类.md` |

一句话判断：

- 改“整套 PPT 怎么组织”：
  先改 `outline.json`
- 改“某一页怎么表达”：
  先改 `slides/*.json`
- 改“图示本身长什么样”：
  先改 `work/assets/*.svg`
- 改“这种页面以后都怎么生成、怎么渲染”：
  再改 prompt 规则和 viewer layout

## 一、如何调整 PPT 的章节结构

### 什么时候算结构问题

通常出现下面这些情况，就应该优先回改章节结构：

- 章节顺序不对
- 章节之间跳跃很大
- 某一章信息明显过多或过少
- 本来应该拆开的内容被塞在同一章
- 某种关键页面缺失，比如总结页、路径页、风险页、练习页

这类问题不要先在 `slides/*.json` 里打补丁。  
因为单页越修，整套 deck 越容易失去节奏。

### 先改哪里

优先修改：

- `work/ppt/项目名/outline.json`

如果你发现“同一类型的项目以后也会经常这样错”，再继续改：

- `skills/prompts/ppt/01_课件类.md`
- `skills/prompts/ppt/02_方案类.md`
- `skills/prompts/ppt/03_汇报类.md`
- `skills/prompts/ppt/04_演示类.md`

### 推荐调整顺序

#### 1. 先看结构，不要先看细节文案

先只回答这几个问题：

- 这套 PPT 属于哪种类型
- 章节数是否合适
- 每章承担的任务是否清晰
- 页序是否顺
- 有没有缺关键页面

#### 2. 调章节，而不是直接调单页

常见结构动作：

- 合并重复章节
- 把过大的章节拆成两章
- 给某章补一个“总览页 / 小结页”
- 把“结论、支撑、动作”拆成连续几页
- 把“问题、方案、计划、风险”拆开

#### 3. 再看每页意图和 layout

结构顺了之后，再继续看：

- 每页是说明、对比、流程、结构、阶段还是图表
- `layout_type` 是否符合页面意图

### 四种类型的默认调整方向

#### `课件类`

优先检查：

- 是否有足够的概念解释页
- 是否有案例页 / 练习页 / 小结页
- 是否把多个知识动作压在一页

常见调整动作：

- 把“概念 + 原理 + 示例”拆成 2-3 页
- 给每章补一页小结
- 给复杂方法补流程图或结构图页

#### `方案类`

优先检查：

- 是否有完整的问题到方案闭环
- 是否把总体方案、实施路径、风险混在一页
- 是否缺决策所需的支撑页

常见调整动作：

- 把“问题 / 目标 / 方案 / 路径 / 风险”拆开
- 给总体方案补结构图或路线图页
- 给风险和保障单独留页

#### `汇报类`

优先检查：

- 是否结论先行
- 关键判断是否有支撑页
- 决策项是否被埋在普通说明里

常见调整动作：

- 给关键结论后面补一页支撑
- 把“问题页”和“下一步页”拆开
- 单独增加“需要支持 / 决策项”

#### `演示类`

优先检查：

- 是否有场景引入
- 亮点页是否足够集中
- 是否节奏太平，像汇报而不像展示

常见调整动作：

- 把多个卖点拆成多页
- 给关键能力补场景页和效果页
- 把过重的说明页压缩成图示页

### 结构调整后的验证方式

至少检查：

- `outline.json` 的章节链路是否顺
- viewer 中大纲是否顺
- 页面顺序是否更自然
- 是否出现新的重复页或空转页

相关文档：

- [工作流](workflow.md)
- [PPT 类型说明](ppt-types.md)

## 二、如何增加 SVG

### 什么时候应该补 SVG

出现下面这些情况时，通常应该增加 SVG，而不是继续堆文字：

- 三层结构、系统构成、架构关系讲不清
- 多对象关系复杂
- 流程、时序、路径、依赖关系难以用 bullet 表达
- 页面虽然信息完整，但看起来太“表格感”或“说明书感”

最常见适用页：

- 架构图
- 关系图
- 路线图
- 流程图
- 依赖图
- 对比结构图

### 先改哪里

通常要同时改两处：

1. SVG 资产文件：
   `work/assets/编号/*.svg`
2. 对应页面 JSON：
   `work/ppt/项目名/slides/*.json`

如果该页本来就应该用 SVG 展示，优先使用：

- `layout_type: "svg_full"`

### 最常见的补 SVG 方式

#### 方式 1：给已有页面补一张真实 SVG

适合：

- 当前页面内容方向对，但表达太文字化

操作：

1. 在 `work/assets/编号/` 下新增 SVG 文件
2. 把该页改成 `svg_full`
3. 在页面 JSON 中填写 `svg.src`

示例：

```json
{
  "layout_type": "svg_full",
  "title": "总体架构",
  "svg": {
    "src": "work/assets/002/010-overall-architecture.svg",
    "alt": "总体架构图",
    "caption": "用结构图代替长段方案说明"
  }
}
```

#### 方式 2：给某一章补一页专门图示页

适合：

- 一整章都缺图形化表达
- 某一段解释总是太重

操作：

1. 先回 `outline.json` 给这一章补一页图示页
2. 重新生成 detail，或手动补一页 `slides/*.json`
3. 再新增对应 SVG

### SVG 放哪里

推荐路径：

```text
work/assets/001/
work/assets/002/
work/assets/003/
```

通常按项目编号分目录管理，这样更容易维护。

### SVG 调整时的注意点

- SVG 应该表达结构，不是把整页文字重新排版进图里
- `svg_full` 页的标题一般由页面标题承担，SVG 内不要重复大标题
- 路径必须真实存在，viewer 和导出都会依赖这个文件
- 如果 viewer 正常但导出不一致，要继续检查导出链路

### 增加 SVG 后怎么验证

先在 viewer 里检查：

- 是否真实加载
- 比例是否正常
- 字是否太小
- 是否重复写标题
- 是否超出页面

再检查导出：

- PPTX 中是否也能正常出现
- 是否有裁切、错位或丢图

相关文件：

- `work/assets/*.svg`
- `work/ppt/项目名/slides/*.json`
- `lib/pptxExport.mjs`

## 三、如何修改 layouts

这里的 “修改 layout” 分三种情况，动作不一样。

### 情况 1：只想让当前项目某一页换一个 layout

这不是全局改 layout，只是项目级调整。

优先修改：

- `work/ppt/项目名/slides/*.json`

例如把某页从：

- `title_bullets`

改成：

- `comparison_table`
- `steps`
- `svg_full`

这种改法最快，但只影响当前项目。

### 情况 2：想让模型以后更容易选对某个 layout

这是规则层调整。

优先修改：

- `skills/prompts/ppt/layouts.md`
- `skills/prompts/ppt/layout_rules.md`
- 对应类型 prompt：`01_课件类.md` ~ `04_演示类.md`

适合场景：

- 同类页面总是被错选为别的 layout
- 某种页面意图缺少明确映射规则
- 想改变某类 PPT 的默认 layout 倾向

### 情况 3：想让某个 layout 本身长得不一样，或新增字段能力

这是渲染层调整。

优先修改：

- `ppt-viewer/src/components/layouts/*.vue`
- `ppt-viewer/src/layoutRegistry.ts`

如果导出也要支持，还要检查：

- `ppt-viewer/src/lib/*`
- `lib/pptxExport.mjs`

### 修改现有 layout 的标准动作

#### 1. 先判断是“规则问题”还是“组件问题”

如果问题是：

- 模型老选错：
  先改 prompt 规则
- 页面已经选对，但长得不好看：
  先改 Vue 组件

#### 2. 如果改了 layout 的外观或字段，要同步文档

需要同步的文档通常包括：

- `docs/zh-CN/layouts.md` 或 `docs/zh-CN/layouts/*.md`
- `skills/prompts/ppt/layouts.md`

如果是中文布局库入口已拆分的页面，就优先更新对应分类页。

#### 3. 如果是新增 layout，要补齐最小闭环

至少包括：

- 一个 Vue 组件
- `layoutRegistry.ts` 注册
- prompt 规则说明
- 中文 layouts 文档说明
- 一个最小样例页用于验证

### 修改 layout 时最容易漏的地方

- 页面组件改了，但 `layoutRegistry.ts` 没注册
- viewer 能看，但导出逻辑没跟上
- prompt 已经写了新 layout，但文档没更新
- 文档里已经有了，但模型并不会优先使用

### layout 调整后的验证顺序

建议按这个顺序：

1. 看 `slides/*.json` 的 `layout_type` 是否正确
2. 打开 viewer 看渲染效果
3. 检查超屏、错位、字段缺失
4. 做一次 PPTX 导出验证
5. 回头补 prompt / docs / examples

相关文档：

- [布局类型库](layouts.md)
- [Fork 指南](fork.md)

## 一条推荐的回改顺序

如果你面对的是一个“整体不太对”的 deck，推荐这样改：

1. 先看 `outline.json`，把章节和页序调顺
2. 再看 `slides/*.json`，把页面意图和 layout 调顺
3. 对需要图形化表达的页补 `work/assets/*.svg`
4. 打开 viewer 检查
5. 再做一次 PPTX 导出检查

不要倒着改。  
先修结构，再修页面，再修资产，最后修渲染一致性，通常最稳。
