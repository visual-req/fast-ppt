# 质量保障

这份文档专门说明：`fast_ppt` 是如何确保生成质量的。

这里说的“质量”，不是单纯指页面好不好看，而是同时包括：

- 结构是否合理
- 页面表达是否匹配意图
- 图形是否真实可用
- viewer 里是否能正常预览
- 导出 PPTX 是否和预览一致
- 同类项目是否能稳定重复生成

也就是说，`fast_ppt` 的目标不是“偶尔生成一套看起来还行的 PPT”，而是尽量把质量变成一个可重复、可检查、可回改的过程。

## 一句话理解

`fast_ppt` 不是靠“模型一次发挥得好”来保证质量，而是靠：

- 分阶段生成
- 中间产物可检查
- 规则先约束
- 图形真实落盘
- viewer 可直接验收
- 导出链路再做一致性检查

这几层一起保证质量。

## 质量不是在哪一步突然出现的

很多工具把质量寄托在最后一轮润色。  
`fast_ppt` 不是这种模式。

它的质量控制是分布在整条链路里的：

1. 输入材料和类型判断
2. `outline.json` 结构检查
3. `deck.json + slides/*.json` 页面检查
4. `work/assets/*.svg` 图形检查
5. viewer 预览检查
6. PPTX 导出一致性检查
7. 文档、示例和 layout 规则沉淀

所以它更像一套带质量门的生产流程，而不是一个单次生成器。

## 一、先用两阶段生成，把大问题拦在前面

质量保障的第一层，是不允许一上来直接生成全部页面。

### 为什么一定先 `outline` 再 `detail`

因为结构问题和页面问题不是同一类问题。

`outline` 负责解决：

- 这是哪种 PPT 类型
- 章节怎么拆
- 页序怎么排
- 哪些页面应该图形化
- 大概应该选什么 layout

`detail` 负责解决：

- 每一页具体写什么
- 用哪种字段组织内容
- 哪些页面需要 SVG
- 哪些页面需要图表、配图或摘要卡片

如果不先过 `outline`，很容易出现：

- 章节顺序整体跑偏
- 关键页缺失
- 图页比例失衡
- detail 阶段越补越乱

所以两阶段流程本身，就是第一道质量门。

## 二、先把产物结构化，才能真正检查

质量保障的第二层，是产物不是一段长文本，而是结构化文件。

核心产物包括：

- `outline.json`
- `deck.json`
- `slides/*.json`
- `work/assets/*.svg`

这件事很关键。  
因为只有结构化了，系统和人才能检查：

- 页序是否连续
- `layout_type` 是否合理
- 字段是否缺失
- 图片 / SVG 路径是否真实存在
- `deck.json` 和 `slides/` 是否同步
- 导出链路是否能读取同一套数据

如果最终只有一段自然语言说明，很多问题其实没法被稳定发现。

相关文档：

- [设计理念](concept.md)
- [项目结构](structure.md)

## 三、先限定类型，再限定页面意图

质量保障的第三层，是先把“生成范围”收窄。

当前固定支持四种类型：

- `课件类`
- `方案类`
- `汇报类`
- `演示类`

这四类不是名字不同，而是结构逻辑不同。

类型一旦明确，很多质量要求就能前置：

- `课件类` 要重知识展开、案例、练习、小结
- `方案类` 要重问题、方案、路径、风险闭环
- `汇报类` 要重结论先行、支撑页、决策项
- `演示类` 要重场景、亮点、节奏和记忆点

同样，页面也不会只按“多写一点说明”处理，而是先判断页面意图：

- 结构
- 对比
- 流程
- 阶段
- 总结
- 图表
- 关系

然后再映射到合适的 `layout_type`。

这能显著降低两类常见质量问题：

- 内容本身对，但页面类型选错
- 页面看起来像 PPT，但表达方式不对

相关文档：

- [PPT 类型说明](ppt-types.md)
- [布局类型库](layouts.md)

## 四、通过 prompt 规则把低质量输出提前拦住

质量保障的第四层，是把很多“容易变差的情况”提前写成规则，而不是等生成后靠人工补救。

这些规则主要在：

- `skills/prompts/ppt/00_PPT生成.md`
- `skills/prompts/ppt/01_课件类.md`
- `skills/prompts/ppt/02_方案类.md`
- `skills/prompts/ppt/03_汇报类.md`
- `skills/prompts/ppt/04_演示类.md`
- `skills/prompts/ppt/layouts.md`
- `skills/prompts/ppt/layout_rules.md`

规则层主要控制这些事情：

- 未确认 `outline.json` 时不能直接进 `detail`
- 不同类型必须满足不同结构要求
- 页面先判断意图，再选 layout
- 结构图 / 流程图 / 关系图优先图形表达
- `svg_full` 不能只是“大段文字换个容器”
- 图页要真实落盘，不允许只写“建议配图”
- 图形要在 16:9 安全区内，不能依赖裁切成立

这类规则的作用是：

- 降低随机性
- 减少低质量常见错误
- 让同类任务更稳定复现

也就是说，质量不是完全靠“结果审美”，而是先靠规则把下限托住。

## 五、图形必须真实落盘，而不是写占位建议

质量保障的第五层，是图形页必须尽量变成真实资产。

尤其是：

- 架构图
- 关系图
- 路线图
- 流程图
- 对比信息图

这类内容如果只写：

- 建议放图
- 可配一张架构图
- 这里适合放示意图

那质量其实没有真正落地。

所以 `fast_ppt` 会尽量要求：

- 直接生成 `work/assets/*.svg`
- 页面 JSON 真实引用这个 SVG
- viewer 直接加载这张图
- 导出链路也使用同一份资产

这层机制解决的是两个非常常见的问题：

1. 图页名义上存在，实际上只是占位
2. 页面表达本质应该图形化，却被大量 bullet 代替

相关文档：

- [调整指南](adjustment.md)
- [美化指南](beautify.md)

## 六、viewer 是真正的质量验收面

质量保障的第六层，是不是“真的能看”，不靠想象判断，而是直接进 viewer 验收。

`ppt-viewer` 会把：

- `deck.json`
- `slides/*.json`
- `work/assets/*.svg`

直接渲染出来。

这意味着很多问题会被立刻暴露：

- 标题不对
- 页面超屏
- layout 选错
- SVG 过密或贴边
- 图片路径失效
- 章节顺序不对
- 同一套 deck 节奏混乱

viewer 的价值，不只是“预览一下”，而是让结果从抽象 JSON 变成可检查页面。

因此，`fast_ppt` 的质量并不是“生成结束时就算结束”，而是至少要经过一轮 viewer 验证。

相关文档：

- [操作手册](manual.md)
- [故障排查](troubleshooting.md)

## 七、viewer 能看还不够，还要检查导出一致性

质量保障的第七层，是 viewer 和 PPTX 导出不能严重背离。

因为实际交付里，很多时候最终看的不是浏览器，而是 `.pptx`。

所以还要检查：

- 图片是否正常出现在导出结果里
- SVG 是否被正确处理
- layout 是否在导出链路里有对应支持
- 字段在导出时有没有丢失
- 风格切换后导出是否一致

这层质量门主要拦截的是：

- viewer 正常，但导出错位
- viewer 支持了新 layout，但导出还没跟上
- 页面看着没问题，但交付文件不能用

所以对 `fast_ppt` 来说，“viewer 可看”不等于“已经通过质量验收”，还要过导出一致性这道门。

## 八、文档、案例和 layout 库本身也在保证质量

质量保障不只发生在生成时，也发生在“让后续任务更稳定”的沉淀里。

仓库里这些内容都在持续提升质量：

- [案例工程](examples.md)：提供真实项目样本
- [布局类型库](layouts.md)：明确 layout 的适用场景和字段
- [PPT 类型说明](ppt-types.md)：降低类型误判
- [调整指南](adjustment.md)：告诉你应该回改哪一层
- [美化指南](beautify.md)：告诉你如何补充高质量视觉素材

这些文档的作用不是“锦上添花”，而是减少两种质量波动：

- 新手不知道该怎么用，导致结果很随机
- 同一个问题每次都靠试错，而不是靠可复用经验解决

## 九、审阅机制让质量不仅看生成者，也看听众视角

质量保障的另一层，是支持从“听众视角”再做审阅。

对应规则文件：

- `skills/prompts/ppt/05_review.md`

这类审阅不会只看单页，而会检查：

- 章节归属
- 页序和承接
- 类型是否跑偏
- 图形页是否承担主表达
- 关键页是否真的有说服力

这能补上一个很关键的盲区：

- 从生成者角度看，内容都在
- 但从听众角度看，不一定好理解，也不一定好决策

所以 `review` 机制，本质上是在补“结果是否真的可交付”的最后一轮质量判断。

## 十、真正的质量闭环，是“生成 -> 检查 -> 回改”

`fast_ppt` 的质量模型不是：

- 生成一次
- 看着差不多
- 结束

而是：

1. 生成
2. 检查
3. 回改
4. 再验证

这就是为什么仓库里会同时存在这些文档：

- [工作流](workflow.md)
- [调整指南](adjustment.md)
- [故障排查](troubleshooting.md)
- [操作手册](manual.md)

它们共同构成的是一个回改闭环，而不是一组零散说明。

## 质量保障可以拆成哪几道门

如果你想快速记住这套机制，可以记这 6 道质量门：

1. **结构门**：必须先过 `outline.json`
2. **规则门**：类型规则、layout 规则、图形规则先约束
3. **页面门**：`deck.json + slides/*.json` 必须结构化可检查
4. **图形门**：SVG / 图片尽量真实落盘，不接受纯占位
5. **预览门**：viewer 中必须可读、可看、可验收
6. **导出门**：PPTX 结果要和 viewer 基本一致

只要缺掉其中一门，质量就很容易退化成“碰运气”。

## 你在实际使用时，最少要做哪些质量动作

如果你是第一次使用，至少做这几步：

1. 先明确 PPT 类型
2. 先检查 `outline.json`，再进 `detail`
3. detail 后检查图页比例、关键页、layout 选择
4. 打开 viewer 检查超屏、错图、错页序
5. 导出一次 PPTX，确认交付文件也正常

这 5 步已经能覆盖大部分高频质量问题。

## 什么时候说明质量机制失效了

如果你反复遇到下面这些情况，就说明应该继续补规则、补文档、补 layout 或补案例：

- 同类项目总是选错类型
- outline 经常缺关键章节
- detail 后大量页面还是文字堆积
- 图页存在但都是占位图
- viewer 能看但导出总出问题
- 新项目质量很依赖“这次 AI 恰好发挥好”

这些都不是单个 deck 的偶发问题，而是质量机制还不够完整的信号。
